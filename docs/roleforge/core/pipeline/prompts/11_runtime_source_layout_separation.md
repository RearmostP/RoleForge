# Stage 11 — Runtime / Source Layout Separation

## Goal

Reorganize the RoleForge repository so that Rust source code and Python runtime package files are physically separated.

The purpose of this stage is to establish a clean distribution architecture before the first PyPI publication.

The core principle is:

> **Source layout and installed runtime layout are separate concerns.**

After this stage:

- Rust source code must live in the conventional Cargo `../../../../../src` tree.
- Python runtime/package files must live under `../../../../../python/roleforge`.
- Building a Wheel must not package Rust source files, Rust tests, development prompts, or other development-only files.
- The resulting Wheel must still support the complete existing RoleForge runtime behavior.
- A Wheel installed into a completely unrelated Python project must still be able to load and execute the existing Test Role.

This is primarily a repository/layout and packaging refactor.

Do not redesign RoleForge behavior.

## 3. Rust Source Tree

Move Rust implementation code out of the Python package tree.

Rust code should live under the standard Cargo:

```text
src/
```

This includes the current Rust implementation such as:

- Core pipeline;
- Loader;
- Main Tokenizer;
- Dispatcher;
- Runtime;
- Handoff;
- Bridges;
- Registry;
- RoleInput;
- Python API bindings;
- crate root;
- subsystem-local Rust tests.

For example, conceptually:

```text
roleforge/lib.rs
→
src/lib.rs
```

and:

```text
roleforge/core/...
→
src/core/...
```

Preserve the existing Rust module architecture.

Do not redesign modules merely because they are being moved.

---

## 4. Rust Tests

Preserve the Stage 10 testing rule:

> **Test code may live beside the subsystem it tests, but it must be physically separated from production implementation code.**

Subsystem-local Rust tests should remain in dedicated `tests.rs` files.

Production modules should only contain the test module declaration when applicable:

```rust
#[cfg(test)]
mod tests;
```

Do not move internal Core unit tests to Cargo root-level integration tests merely for consistency.

Do not make private or `pub(crate)` APIs public just to make tests work.

---

## 5. Python Runtime Package

The Python package distributed to users must live under:

```text
python/roleforge/
```

It should contain runtime files needed by an installed RoleForge package.

At minimum, preserve the current required Python runtime files:

```text
python/roleforge/__init__.py
python/roleforge/_live.py
```

The compiled native module:

```text
roleforge/_native.pyd
```

is generated by Maturin and must continue to be exposed as:

```python
roleforge._native
```

Do not change the public import behavior.

Existing imports such as:

```python
from roleforge import load
```

must continue to work unchanged.

## 6. Maturin Configuration

Configure the mixed Rust/Python project using the separated Python source tree.

The intended configuration concept is:

```toml
[tool.maturin]
bindings = "pyo3"
module-name = "roleforge._native"
python-source = "python"
```

Verify this against the installed/current Maturin behavior before finalizing it.

Do not blindly apply configuration if the actual project requires an additional supported Maturin setting.

The resulting Wheel must contain the Python runtime package and compiled native extension, but must not accidentally package the Rust source tree.

## 8. Runtime Path Resolution

Do not assume that runtime resources can continue to be resolved through the old source-tree layout.

Inspect all current uses of:

```rust
CARGO_MANIFEST_DIR
```

and any equivalent source-root assumptions.

After installation, RoleForge must resolve runtime resources relative to the **installed RoleForge package**, not relative to the original Git repository or Rust compilation directory.

The important distinction is:

```text
Compile-time source location
≠
Installed runtime package location
```

Design the smallest clean mechanism necessary to locate RoleForge runtime resources after installation.

It must work when:

- the Git repository is not present;
- the Wheel was installed into another project's virtual environment;
- the current working directory is unrelated to RoleForge;
- RoleForge is imported normally through Python.

Do not introduce a broad resource-management framework unless it is actually necessary.

Preserve the architectural rules:

> **The Core resolves destinations, not implementations.**

> **Core knows the protocol, never the roles.**

The solution must not introduce hardcoded knowledge of `Test`, `Directory`, or any other specific Role into Core.

## 9. Wheel Content Boundary

After this stage, the Wheel must not contain development-only Rust/source material such as:

```text
*.rs
Rust tests
pipeline/prompts/
historical development prompts
```

It should contain only files required for the installed Python runtime and normal Python packaging metadata.

Conceptually, the runtime package should resemble:

```text
roleforge/
├── __init__.py
├── _live.py
├── _native.pyd
│
├── core/
│   └── storage/
│       ├── builtin_roles.json
│       └── dynamic_roles.json
│
├── builtin_roles/
└── roles/
    └── Test/
        └── main.py
```

Do not treat this example as permission to remove a runtime file that the current implementation actually requires.

Inspect first.

- `project.test[0]`;
- `project.test[1]`;

> **Core defines the data. Bridge adapts it to the target environment. Role defines the behavior.**

And:

> **The Core resolves and delivers. The Role decides what happens next.**

`load()` must still NOT automatically call `start()`.

Do not implement the `start()` lifecycle in this stage.
