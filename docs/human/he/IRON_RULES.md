# כללי הברזל של RoleForge למפתחים

[לתיעוד הראשי](README.md) · [English](../en/IRON_RULES.md) · [יצירת Roles](CREATING_ROLES.md)

הכללים האלה מתארים מה צריך להישאר נכון כשהפרויקט מתפתח. זהו מדריך ארכיטקטוני קצר, ולא רשימת קבצים או מפרט מימוש מלא. [כללי הברזל המפורטים ל־AI](../../ai/CORE_IRON_RULES.md) מכילים את ההגבלות המעמיקות יותר לעבודת הפיתוח.

1. **Core מכיר את הפרוטוקול, לא את ה־Roles.** הוא מזהה הצהרות RoleForge, שומר את הנתונים ומנתב אותם. הוא אינו אמור לדעת מה פירושה של פקודה בגוף של Role.

2. **המקור קובע מהו ה־Role; ה־Role קובע את ה־API וההתנהגות שלו.** ההצהרה `@role Test` קובעת את הזהות שהתגלתה. הרישום מספק יעד; מחלקת מימוש או import אינם תחליף לגילוי במקור.

3. **גילוי ה־Roles קודם לחשיפת התנהגות ייעודית שלהם.** קודם מבררים אילו מופעים קיימים והיכן הם מופיעים. ממשק נוח אינו רשאי להניח זהות של Role בלי לבדוק את המקור. API דינמי לגישה ל־Roles עדיין אינו ממומש.

4. **הרכיבים מעבדים; Runtime מתאם.** Loader קורא, Main Tokenizer מגלה, Registry פותר רישומים, Dispatcher מפיק תוצאות ניתוב ו־Handoff מוצא Bridge למסירה. Runtime קובע את הסדר. רכיב מרכזי אינו צריך לקבל אחריות להפעלת הרכיב המרכזי הבא.

5. **Core פותר יעדים, לא מימושים.** לצורך ניתוב נדרשים יעד רשום ומזהה Bridge. אין צורך להסתעף לפי הטיפוסים הפנימיים, התחביר או ההתנהגות של Role מסוים.

6. **Core פותר ומוסר; ה־Role מחליט מה קורה אחר כך.** קבלה מוצלחת היא גבול האחריות. ה־Role יכול לנתח, לבדוק, לשמור את המופע, להכין API או לא לעשות דבר. Core אינו מנהל את מחזור החיים הפנימי שלו.

7. **כל Role מקבל את אותו חוזה RoleInput לוגי.** הנתונים הניטרליים שייכים ל־Core: שם, שני האינדקסים, גוף ומידע מקור. Bridges מתאימים את הייצוג לסביבת היעד בלי להמציא אינדקסים או לאבד מידע.

8. **מזהי Bridge בוחרים רישום, ולא מצהירים על שפת תכנות.** `via: "python"` בוחר את ה־Bridge הרשום בשם המדויק הזה. שם ה־Role או הסיומת `.py` אינם תחליף לבחירה מפורשת.

9. **roleforge_receive הוא מסירה, לא start.** ה־receiver המחייב ב־Python מקבל את הקלט שנמסר. עצם הקבלה אינה הוראה ל־Core להפעיל `start()` או פעולה אחרת שה־Role מציע למשתמש. מחזור חיים סופי של start בניהול Core אינו קיים כרגע.

10. **כל Role אחראי לשפה שלו.** tokenizer, parser, בדיקות ומשמעות ייעודיים שייכים ל־Role. מממשים רק את החלקים שצריך; אין חובה למסלול עם parser, ואין Main Parser ב־Core.

11. **הוספת Role לא אמורה לדרוש ללמד את Core מה הוא אומר.** מימוש Python ורשומת Registry צריכים להשתלב בחוזה המסירה הקיים. אם צריך תנאי לפי שם ה־Role בתוך Core, כדאי לבדוק מחדש את חלוקת האחריות.

12. **מתקנים בזבוז ברור מיד; דוחים אופטימיזציה ארכיטקטונית.** אפשר להסיר העתקות מיותרות או עבודה חוזרת כשהשינוי פשוט ובטוח. אין צורך להוסיף מטמונים, מקביליות או ארכיטקטורה רחבה רק בגלל צורך עתידי משוער.

13. **פרט שלא הוכרע אינו החלטה.** דוגמה, רעיון סביר או פרומפט ישן אינם מגדירים חוזה עתידי. מסירת Rust, ה־API הסופי של Roles, aliases, אריזה ו־Error/Console Managers נשארים פתוחים במקומות שבהם לא התקבלה החלטה מפורשת.

שני תנאים נוספים תומכים בכללים: לאורך המסירה שומרים על הסדר הגלובלי, האינדקס לפי שם ומידע המקור; כשאותו שם מופיע ברישום המובנה והדינמי, אין לבחור אחד מהם בשקט. בדיקת הקונפליקטים הנוכחית מונעת כל מסירה באותה טעינה. [המבוא](README.md) מבחין בין העקרונות הקבועים לבין התנהגות הדיווח הזמנית.
